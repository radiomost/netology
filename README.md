# 2. Определение количества рабочих нод

Минимально кластер мог бы работать на одной большой ноде.

Однако Kubernetes предполагает отказоустойчивость, поэтому рабочие нагрузки необходимо распределить минимум по нескольким узлам.

Выбираем **3 worker-ноды**.

При выходе одной ноды из строя две оставшиеся должны принять её нагрузку.

Следовательно:

```
17 CPU / 2 = 8.5 CPU
30 ГБ / 2 = 15 ГБ RAM
```

Значит каждая рабочая нода должна иметь ресурсов больше этих значений.

Выбираем характеристики одной worker-ноды:

- **8 vCPU**
- **16 ГБ RAM**

Общий объем рабочих ресурсов:

| Количество | CPU | RAM |
|------------|----:|----:|
| 3 worker | 24 vCPU | 48 ГБ |

После отказа одной ноды останется:

- **16 vCPU**
- **32 ГБ RAM**

CPU будет немного меньше расчетных 17 vCPU, поэтому разумнее выбрать рабочие узлы с запасом.

Окончательный вариант:

**3 worker-ноды по 10 vCPU и 16 ГБ RAM.**

Общие ресурсы:

- **30 vCPU**
- **48 ГБ RAM**

После выхода одной ноды останется:

- **20 vCPU**
- **32 ГБ RAM**

Этого достаточно для размещения всего приложения.

# 3. Служебные ресурсы Kubernetes

Кроме пользовательских приложений на каждой рабочей ноде работают системные компоненты Kubernetes:

- kubelet;
- kube-proxy;
- Container Runtime;
- CNI-плагин;
- системные Pods.

Для них рекомендуется зарезервировать примерно:

- **0.5 vCPU**
- **1 ГБ RAM**

на каждую рабочую ноду.

Поэтому фактически каждая worker-нода должна иметь:

- **10 vCPU**
- **16 ГБ RAM**

# 4. Control Plane

Для обеспечения отказоустойчивости рекомендуется использовать **3 control-plane-ноды**.

На них работают:

- kube-apiserver;
- etcd;
- scheduler;
- controller-manager.

Рекомендуемые характеристики одной control-plane-ноды:

- **2 vCPU**
- **4 ГБ RAM**

Итого:

| Количество | CPU | RAM |
|------------|----:|----:|
| 3 control-plane | 6 vCPU | 12 ГБ |

# Вывод

Для размещения приложения необходим Kubernetes-кластер следующей конфигурации:

- **3 control-plane-ноды** по **2 vCPU и 4 ГБ RAM**;

Такой кластер:

- обеспечивает отказоустойчивость приложения;
- выдерживает отказ одной рабочей ноды без остановки сервисов;
- имеет запас ресурсов для системных компонентов Kubernetes и дальнейшего масштабирования.
