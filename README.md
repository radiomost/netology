## 1 Создание облачной инфраструктуры

В дипломном проекте использовались ресурсы имеющейся домашней инфраструктуры.
Упрощенная схема домашней лаборатории для выполнения проекта приведена на [схеме](img/shems_home_lab.jpg):

![схеме](img/shems_home_lab.jpg)

Для обеспечения безопасности проекта, использовались имеющиеся приложения внутренней инфраструктуры, такие как `HashiCorp Vault` и `MinIO S3`.

Вся разработка производится на удаленной виртуальной машине в сети домашней инфраструктуры гипервизора Proxmox. Требования, предьявляемые к виртуальной машине:
1. CPU не менее 2-х
2. RAM не менее 4GB
3. HDD не менее 32GB
4. Настроенный внутренний(зона rdmost-lab.ru) и внешний DNS (8.8.8.8, 1.1.1.1)
5. Авторизация по SSH с пользованием усиленной защитой при помощи RuToken
6. Внешний internal FW настроен с разрешающими правилами для доступа к сервисам сегмента сети `Net Service` в Internal сети.
7. Обращение к внтренним сервисам осущетсвляется с использованием протокола `HTTPS` и сертификатов, подписанных внутренним CA сограниченным сроком жизни.
8. Внутренний CA добавлен в доверенные CA.
9. Доступ к Vault осуществляется только текущему пользователю по его учетке. Креды для подключения не хранятся в папке проекта, а находятся в конфигурационных файлах
пользователя. Имееют ограниченный TTL. Подружаются в проект через переменные окружения в момент сборки и деплоя проекта.
10. Все секреты (YandexCloud, S3, рутовые, ssh-key) необходимые для сборки и деплоя проекта находятся исключительно в `HashiCorp Vault`.

Так как секреты хранятся во внутренней сети, то при сборке и деплое в GitHub доступа к секретам нет.
Для  реализации автоматизированной сборки и деплоя CI/CD используется так же внутренний сервис GitLab, который имее доступ к внуренним сервисам.


### 1.2 Создание сервисного аккаунта с необходимыми правами

Для безопасной автоматизации Terraform не должен использовать персональные токены с правами суперпользователя. Вместо этого создается выделенный сервисный аккаунт (Service Account, SA) с принципом наименьших привилегий (Principle of Least Privilege). 

Конфигурация для этого этапа изолирована в папке `stage0-bootstrap`, что соответствует требованию диплома хранить конфигурации bootstrap-ресурсов и основной инфраструктуры в разных директориях.

#### Шаг 1.2.1: Создание SA (Service Account) 

Создается сервисный аккаунт, который будет использоваться для управления ресурсами.
[stage0-bootstrap](stage0-bootstrap/main.tf).

**Результат:** В консоли Yandex Cloud (раздел Service Accounts) создан аккаунт 'diplom-project-bootstrap-sa'.

#### Шаг 1.2.2: Назначение ролей

Сервисному аккаунту назначается роль storage.admin на уровне папки. Этого достаточно для создания и управления S3-бакетами (включая backend), но запрещает несанкционированное изменение других ресурсов облака.
[stage0-bootstrap](stage0-bootstrap/main.tf)

**Результат:** В разделе Access bindings этого аккаунта или на уровне Folder подтверждена роль storage.admin.

#### Шаг 1.2.3: Создание статического ключа доступа

Для аутентификации Terraform в S3-совместимом хранилище (backend) необходимы статические ключи (Access Key и Secret Key), привязанные к сервисному аккаунту.
[stage0-bootstrap](stage0-bootstrap/main.tf)

**Результат:** Сгенерированы ключи, которые выводятся в консоль как sensitive переменные (static_access_key и static_secret_key).
Эти ключи будут использованы в конфигурации provider.tf для основной инфраструктуры (stage1-infra), а также для настройки профиля minio-s3 в локальном окружении или CI/CD.

**Безопасность:** Статические ключи никогда не коммитятся в Git. Они передаются через переменные окружения или защищенные хранилища секретов (Secret Manager).

### 1.3 Развертывание сети (VPC, подсети в разных зонах доступности)

Для обеспечения отказоустойчивости будущего Kubernetes-кластера и соответствия best practices, сетевая инфраструктура разворачивается в нескольких зонах доступности. Конфигурация 
вынесена в отдельную директорию `stage1-network/`, чтобы отделить её от bootstrap-ресурсов, как того требует задание.
[stage1-network](stage1-network/main.tf)

#### Шаг 1.3.1: Создание VPC

Создается базовая виртуальная сеть (VPC), которая объединит все ресурсы проекта.

```hcl
resource "yandex_vpc_network" "k8s_network" {
  name        = "${var.project_name}-vpc"
  description = "VPC network for K8s infrastructure"
}
```

#### Шаг 1.3.2: Создание подсетей

Для регионального кластера необходимо минимум две зоны доступности. Создаем подсети в зонах ru-central1-a и ru-central1-b с непересекающимися CIDR-блоками.
[stage1-network](stage1-network/main.tf)

#### Шаг 1.3.3: Настройка маршрутизации (опционально для начала, но важно для K8s)

В Yandex Cloud по умолчанию маршрутизация внутри VPC работает автоматически: ресурсы в разных подсетях одной сети видят друг друга без дополнительных настроек.
Для доступа нод K8s в Интернет (например, для скачивания образов контейнеров) обычно используют NAT Gateway. Однако, для строгой экономии бюджета купона, мы откажемся от создания платного NAT Gateway. Вместо этого, на следующем этапе (создание ВМ), мы будем назначать публичные IP-адреса непосредственно на сетевые интерфейсы виртуальных машин. Это полностью закрывает потребность в исходящем и входящем интернете без дополнительных затрат на сетевое оборудование.

#### Конфигурация бэкенда для stage1:
Чтобы Terraform использовал единое хранилище состояний, в stage1-network/provider.tf настроен тот же S3 backend, что и в stage0, но с уникальным ключом:
```hcl
backend "s3" {
  bucket = "netology"
  key    = "stage1-network.tfstate" # Уникальный ключ для сетевой инфраструктуры
  # ... остальные настройки s3-api.rdmost.ru
}
```

## 2. Создание Kubernetes кластера
### 2.1 Самостоятельная установка K8s на VM (через Terraform + Ansible/Kubespray).

Самостоятельная установка Kubernetes (Self-hosted) через Terraform и Kubespray — это классический и наиболее ценный для DevOps-инженера подход. Он позволяет полностью контролировать инфраструктуру и глубже понимать внутреннее устройство кластера.
Для выполнения этого этапа мы создадим новую директорию stage2-compute/, где с помощью Terraform развернем 3 виртуальные машины (1 Master и 2 Worker), а затем используем Ansible и Kubespray для установки Kubernetes.

#### Шаг 2.1.1: Создание вычислительных ресурсов (Terraform)

С помощью Terraform создается 3 виртуальные машины в разных зонах доступности (`ru-central1-a` и `ru-central1-b`). 

**Замечание** Так как с высокой вероятностью автоматически назначенные внешние IP адреса виртуальным машинам РКН блокирует, то я в ручном режиме создал публичные IP адреса и проверил их (через отдельную VM), что они не заблокированы РКН. Эти статические IP адреса я внес в переменные проекта [terraform.tfvars](stage2-compute/terraform.tfvars)

**Оптимизация бюджета:**
- **Master node:** 2 vCPU, 4 GB RAM, `preemptible = false`. Мастер критичен для работы кластера, поэтому он не должен прерываться.
- **Worker nodes:** 2 vCPU, 4 GB RAM, `preemptible = true`. Использование прерываемых ВМ для воркеров позволяет существенно экономить бюджет купона.
- **Сеть:** Всем ВМ назначаются публичные IP-адреса (`nat = true`) для обеспечения доступа из Интернета и возможности скачивания Docker-образов.

**Файл:** [stage2-compute/main.tf](stage2-compute/main.tf)

!['img_3.png'](img/img_3.png)

#### Шаг 2.1.2: Настройка Ansible и подготовка inventory

После успешного создания виртуальных машин через Terraform (`terraform apply` в папке `stage2-compute`), необходимо подготовить Ansible inventory для Kubespray. Этот процесс полностью автоматизирован через Makefile и bash-скрипты, что исключает ручные операции и ошибки.

### Автоматизация через Makefile

Для управления процессом развертывания Kubernetes кластера используется система целей (targets) в Makefile, расположенном в корне проекта. Это обеспечивает воспроизводимость и упрощает процесс для других участников команды.

```mermaid
treeView-beta
netology/ # Основной Makefile с целями автоматизации
  Makefile
  scripts/
    setup-kubespray.sh # Bash-скрипт для настройки Kubespray
  stage2-compute/ # Terraform конфигурация ВМ
  kubespray/ # Клонируется автоматически при выполнении make kubespray-init
``` 

> [!WARNING]
> Перед установкой kuberspray необходимо в ручную через  WebUI консоль YandexCloud. Удалить автоматически назначенные IP адреса и заменить их на подготовленные "белые" IP

### Инициализация Kubespray

Первым шагом является клонирование репозитория Kubespray и настройка Python-окружения для работы с Ansible.
```bash
make kubespray-init
```

**Что делает команда `make kubespray-init`:**

1. **Проверка окружения:** Скрипт проверяет наличие необходимых директорий (`stage2-compute`) и инструментов (`pyenv`, `git`).

2. **Клонирование Kubespray:** Если директория `kubespray` не существует, клонирует официальный репозиторий:
  ```bash
  git clone https://github.com/kubernetes-sigs/kubespray.git
  ```
Настройка Python-окружения: Создает изолированное виртуальное окружение с помощью pyenv:

```bash
pyenv virtualenv 3.12.10 netology
pyenv local netology
```
Это гарантирует, что зависимости Kubespray не конфликтуют с системными пакетами Python.

**Установка зависимостей:** Устанавливает все необходимые Python-библиотеки из requirements.txt:

```bash
    pip install -r requirements.txt
```
Основные зависимости включают Ansible, Jinja2, Python-клиенты для Kubernetes и другие утилиты.

**Подготовка inventory:** Копирует шаблонный inventory из inventory/sample в inventory/mycluster:
```bash
cp -rfp inventory/sample inventory/mycluster
```
**Получение IP-адресов:** Автоматически извлекает внешние IP-адреса виртуальных машин из Terraform state:

```bash
MASTER_IP=$(terraform output -raw master_external_ip)
WORKER1_IP=$(terraform output -json workers_external_ips | jq -r '."worker-1"')
WORKER2_IP=$(terraform output -json workers_external_ips | jq -r '."worker-2"')
```
**Ожидаемая структура:**
* Master node (node1) назначена в группу kube_control_plane и etcd
* Worker nodes (node2, node3) назначены в группу kube_node
* Все IP-адреса соответствуют внешним IP виртуальных машин
* Все ноды включены в группу k8s_cluster
Если IP-адреса изменились (например, после пересоздания ВМ), можно перегенерировать inventory без повторной инициализации:

```bash
make kubespray-inventory
```

**Что делает команда make kubespray-deploy:**
1. **Проверка наличия inventory:** Убеждается, что файл kubespray/inventory/mycluster/hosts.yaml существует.
2. **Запуск Ansible playbook:** Выполняет основной playbook Kubespray:

```bash
ansible-playbook -i inventory/mycluster/hosts.yaml \
-u ubuntu \
-b --become-user=root \
--private-key=~/.ssh/id_rsa \
cluster.yml
```
3. **Процесс установки:** Kubespray автоматически выполняет следующие задачи:
* Установка Docker/containerd на все ноды
* Настройка kubeadm, kubelet, kubectl
* Инициализация control plane на master ноде
* Присоединение worker нод к кластеру
* Установка CNI плагина (Calico по умолчанию)
* Развертывание CoreDNS для DNS в кластере
* Настройка kube-proxy для сетевой маршрутизации
* Установка метрик-сервера для мониторинга ресурсов
4. **Время выполнения:** Процесс занимает 10-15 минут в зависимости от скорости интернета (большая часть времени уходит на скачивание контейнерных образов).
5. **Результат:** После успешного завершения все ноды должны быть в статусе Ready, а системные поды в namespace kube-system в статусе Running.

**Получение kubeconfig для доступа к кластеру**
После успешного развертывания кластера необходимо получить файл конфигурации 'kubeconfig' для управления кластером через 'kubectl'.

```bash
make k8s-kubeconfig
```

### Что делает эта цель (пошагово):
|Шаг|Действие|
|---|---|
|1|Автоматически получает IP мастера из terraform output (не нужно вводить вручную)|
|2|Создает директорию ~/.kube|
|3|Подключается к мастеру и копирует /root/.kube/config в /tmp с правами для ubuntu|
|4|Скачивает файл через scp в ~/.kube/config|
|5|Удаляет временный файл на мастере|
|6|Заменяет внутренний IP (10.10.0.x) на внешний IP мастера в конфиге|
|7|Устанавливает права 600 на kubeconfig|

### Управление Kubernetes-кластером и развертыванием (Makefile)
|Команда|Назначение|Что выполняет под капотом|
|---|---|---|
|**`make k8s-setup`**|**Полная первоначальная настройка доступа** (рекомендуется при первом запуске).|Последовательно запускает цепочку: получение `kubeconfig` с мастер-ноды → создание SSH-туннеля → проверку доступности кластера.|

#### Нюансы аутентификации в Yandex Container Registry (YCR)
При автоматическом создании секрета `imagePullSecrets` для Kubernetes через Makefile критически важны два момента:
1. **Имя пользователя:** При аутентификации через IAM-токен параметр `--docker-username` должен быть строго равен `iam` (а не `json` или `oauth`).
2. **Очистка токена:** Команда `yc iam create-token` часто добавляет скрытый символ переноса строки (`\n`) в конец вывода. Если передать его в Kubernetes "как есть", base64-кодирование секрета будет некорректным, что приведет к ошибке `401 Unauthorized` при попытке скачать образ. 

Для решения этой проблемы в Makefile используется конвейер `tr -d '\n\r'`, который гарантирует передачу "чистого" токена:

```makefile
ycr_token=$$(yc iam create-token | tr -d '\n\r') && \
kubectl create secret docker-registry ycr-secret \
    --docker-server=cr.yandex \
    --docker-username=iam \
    --docker-password="$$ycr_token" \
    -n default --dry-run=client -o yaml | kubectl apply -f -
```

## 5. Установка и настройка CI/CD

Для обеспечения принципов непрерывной интеграции и непрерывной доставки (CI/CD), а также для автоматизации рутинных операций была выбрана и глубоко интегрирована система GitLab CI/CD. Архитектура проекта разделена на два независимых репозитория: netology-diploma-app (исходный код приложения) и netology (Infrastructure as Code, конфигурация Kubespray и манифесты деплоя). Такое разделение обеспечивает четкое разделение ответственности (Separation of Concerns), повышает безопасность и позволяет масштабировать процессы сборки и развертывания независимо друг от друга.

### 5.1 Настройка автоматической сборки Docker-образа при коммите в репозиторий приложения

Автоматическая сборка контейнеризированного приложения настроена в репозитории netology-diploma-app и срабатывает при любом событии push в основную ветку (diplom-dev).

#### Шаг 5.1.1: Создание конфигурационного файла пайплайна

В корне репозитория приложения создан файл .gitlab-ci.yml. В нем определена стадия build_and_push. В качестве исполняемого окружения (Docker image) используется официальный легковесный образ docker:24.0.5, что гарантирует наличие актуальных и безопасных утилит для работы с контейнерами. Для оптимизации времени выполнения и надежности процесса, этапы сборки и отправки образа объединены в одну джобу (job), что исключает накладные расходы на передачу артефактов между этапами и снижает вероятность рассинхронизации окружения.

#### Шаг 5.1.2:  Настройка аутентификации в Yandex Container Registry (YCR)

Для безопасной загрузки образов в приватный реестр используется механизм IAM-аутентификации Яндекс.Облака, исключающий хранение статических паролей. В настройках CI/CD репозитория (Settings → CI/CD → Variables) добавлена защищенная переменная YC_SA_KEY (тип File или Variable), содержащая JSON-ключ сервисного аккаунта с минимально необходимыми правами (container-registry.images.pusher).
В секции before_script пайплайна этот ключ сохраняется во временный файл, после чего с помощью утилиты yc генерируется свежий, короткоживущий IAM-токен. Этот токен динамически передается в команду docker login --username iam --password-stdin cr.yandex, обеспечивая безопасный доступ на время выполнения джобы.

#### Шаг 5.1.3 Сборка и отправка образа в реестр
На этапе script выполняются команды docker build для создания образа на основе Dockerfile репозитория. Для обеспечения полной трассируемости (traceability) и возможности отката, образу присваиваются два тега:
1. Уникальный короткий хеш текущего коммита ($CI_COMMIT_SHORT_SHA), позволяющий однозначно идентифицировать версию кода, из которой собран образ.
2. Тег latest, используемый для удобства развертывания в средах, где не требуется строгая фиксация версии.
После успешной сборки образы отправляются в Yandex Container Registry с помощью команды docker push.


### 5.2 Настройка автоматического деплоя нового образа в Kubernetes

Развертывание инфраструктуры и последующий деплой приложения в кластер Kubernetes управляются из репозитория netology. Для унификации команд и соблюдения принципа DRY (Don't Repeat Yourself) вся сложная логика инкапсулирована в цели файла Makefile, которые пайплайн вызывает как исполняемые скрипты.

#### Шаг 5.2.1: Триггер пайплайна по тегу и подготовка окружения

В соответствии с требованиями к автоматизации, для управления инфраструктурой настроен полноценный Terraform-пайплайн:
* Валидация и Планирование (tf-validate, tf-plan): Автоматически запускаются при создании Merge Request. Джоба tf-plan генерирует бинарный план и текстовый отчет, который с помощью GitLab API автоматически публикуется в виде комментария к MR. Это позволяет ревьюверам оценить изменения до их применения.
* Применение изменений (tf-apply): Запускается вручную (when: manual) только после слияния кода в основную ветку. Это критически важное ограничение безопасности, предотвращающее автоматическое разрушение или изменение продакшен-инфраструктуры без явного подтверждения инженера.

#### Шаг 5.2.2: Безопасное получение конфигурации кластера и параметров реестра

Поскольку проект требует специфических версий инструментов, в базовом шаблоне пайплайна (.base) реализован механизм их загрузки. На этапе инициализации скрипт скачивает архивы с внутреннего репозитория артефактов (repository.rdmost.ru), игнорируя самоподписанные SSL-сертификаты (флаг -k). Распаковываются кастомная версия Terraform (v1.14.0) и провайдер Yandex Cloud (v0.129.0). Далее настраивается файл ~/.terraformrc на использование локального зеркала (filesystem mirror), что ускоряет последующие инициализации и гарантирует воспроизводимость сборок.

#### Шаг 5.2.3: Автоматизация развертывания Kubernetes (Kubespray)

Для избежания проблем с потерей контекста и виртуального окружения между разными джобами GitLab CI, процессы инициализации, создания инвентаря и деплоя Kubespray объединены в единую джобу kubespray-deploy-cluster:
1. **Настройка SSH**: В начале выполнения джобы (в блоке script) приватный SSH-ключ из переменной SSH_PRIVATE_KEY безопасно записывается в ~/.ssh/id_rsa, очищается от символов переноса строки (\r) и защищается правами 600.
2. **Инициализация (make kubespray-init)**: Скрипт клонирует репозиторий Kubespray, фиксирует стабильную версию (v2.25.0) и разворачивает изолированное Python-окружение (venv), устанавливая необходимые зависимости (Ansible, netaddr и др.) с использованием зеркал для обхода сетевых таймаутов.
3. **Генерация инвентаря (make kubespray-inventory)**: Скрипт обращается к состоянию Terraform стадии stage2-compute, извлекает актуальные внутренние и внешние IP-адреса мастер- и worker-нод, и динамически генерирует файл kubespray/inventory/mycluster/hosts.yaml, явно указывая пользователя ubuntu и путь к SSH-ключу.
4. **Деплой кластера (make kubespray-deploy)**: Makefile активирует виртуальное окружение и запускает ansible-playbook, который настраивает Kubernetes на целевых виртуальных машинах.

#### Шаг 5.2.4: Деплой приложения и стека мониторинга в Kubernetes
После успешного развертывания кластера запускается джоба деплоя приложения:
1. **Подключение к кластеру (make k8s-ci-connect)**: Пайплайн устанавливает SSH-туннель к мастер-ноде, скачивает файл admin.conf и локально адаптирует его для обращения к API-серверу через 127.0.0.1:6443.
2. **Подготовка секретов**: С помощью утилиты sed в манифесте app-deployment.yaml динамическая заглушка __REGISTRY_ID__ заменяется на реальный ID реестра, извлеченный через terraform output. Создается Kubernetes Secret типа docker-registry (ycr-secret), использующий свежий IAM-токен для скачивания приватного образа.
3. **Применение манифестов**: Выполняется kubectl apply для Deployment, Service и Ingress. Пайплайн блокируется командой kubectl wait до момента перехода подов приложения в состояние Ready.
4. **Развертывание Helm-чартов**: Устанавливаются Ingress-контроллер (с типом сервиса LoadBalancer для получения внешнего IP от облачного провайдера, что является современной практикой вместо hostNetwork) и стек мониторинга kube-prometheus-stack.

### 5.3 Архитектура и конфигурация среды исполнения GitLab CI/CD

В качестве основного инструмента автоматизации был выбран GitLab CI/CD, так как он предоставляет нативную интеграцию с репозиторием кода, единый интерфейс для управления задачами и секретами, а также гибкую систему раннеров.

#### Шаг 5.3.1: Развертывание и конфигурация GitLab Runner

На выделенной виртуальной машине h-devops установлен и зарегистрирован собственный (self-hosted) GitLab Runner. В конфигурационном файле /etc/gitlab-runner/config.toml настроен исполнитель docker с параметром privileged = true, что необходимо для корректной работы вложенных контейнеров (Docker-in-Docker) при сборке образов. Для решения проблем с разрешением внутренних доменных имен корпоративной сети, в конфигурацию добавлен параметр extra_hosts, явно указывающий на внутренние IP-адреса сервисов GitLab и S3-совместимого хранилища (MinIO).

#### Шаг 5.3.2: Централизованное управление секретами и безопасность

Соблюдение принципов информационной безопасности является приоритетом. Все чувствительные данные (JSON-ключи сервисных аккаунтов, приватные SSH-ключи, учетные данные для S3-бэкенда Terraform) хранятся исключительно в защищенных переменных GitLab CI/CD (Settings → CI/CD → Variables). Для переменных включены флаги Masked (чтобы их значения не попадали в логи даже в виде хэшей) и File (для корректной передачи многострочных данных, таких как приватные ключи, без искажения переносов строк). В исходном коде репозитория эти данные полностью отсутствуют.

#### Шаг 5.3.3: Реализация принципа DRY (Don't Repeat Yourself)

Для обеспечения идентичности поведения при локальной разработке инженера и в автоматизированном конвейере CI/CD, все сложные последовательности команд инкапсулированы в цели файла Makefile (например, make plan, make kubespray-init, make k8s-deploy). Пайплайн GitLab CI выступает в роли оркестратора, который лишь подготавливает окружение и вызывает эти цели. Это позволяет разработчику выполнить всю процедуру деплоя локально одной командой, будучи уверенным, что в CI/CD будет выполнен абсолютно тот же набор действий.
