## Задание 1. Выбрать стратегию обновления приложения и описать ваш выбор

1. Имеется приложение, состоящее из нескольких реплик, которое требуется обновить.
2. Ресурсы, выделенные для приложения, ограничены, и нет возможности их увеличить.
3. Запас по ресурсам в менее загруженный момент времени составляет 20%.
4. Обновление мажорное, новые версии приложения не умеют работать со старыми.
5. Вам нужно объяснить свой выбор стратегии обновления приложения.

## Решение

### Анализ возможных стратегий

#### Recreate

Преимущества:

- отсутствуют проблемы совместимости между версиями;
- простая стратегия обновления.

Недостатки:
- во время обновления приложение полностью недоступно.
Для данного задания стратегия **не подходит**, так как приложение должно оставаться доступным.

---

#### RollingUpdate

Преимущества:
- отсутствует простой приложения;
- обновление происходит постепенно;
- возможен автоматический откат.

Недостатки:
- некоторое время одновременно работают две версии приложения.

Поскольку новая версия несовместима со старой, необходимо исключить одновременную работу разных версий.
Это можно сделать, настроив RollingUpdate следующим образом:

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 1
    maxSurge: 0
```

Такая конфигурация означает:

- перед созданием нового Pod сначала удаляется один старый;
- одновременно никогда не создаются дополнительные Pod;
- не требуется дополнительная память;
- расход ресурсов не превышает текущий.

Свободных ресурсов в размере 20% недостаточно для полноценного запуска второй версии приложения, поэтому использование `maxSurge > 0` нежелательно.

---

#### Blue/Green

Преимущества:
- быстрое переключение;
- простой откат.

Недостатки:
- необходимо одновременно содержать две полные версии приложения;
- требуется практически удвоенный объем ресурсов.

При имеющемся запасе ресурсов стратегия неприменима.

---

### Canary

Преимущества:
- постепенное внедрение новой версии;
- возможность быстро остановить обновление.

Недостатки:
- некоторое время одновременно работают несовместимые версии приложения.

Для данного случая стратегия также неприменима.

---

# Выбранная стратегия

Наиболее подходящей является **RollingUpdate** со следующими параметрами:

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 1
    maxSurge: 0
```

Причины выбора:

- приложение остается доступным;
- не требуется дополнительная память;
- обновление происходит постепенно;
- поддерживается автоматический rollback;
- отсутствует превышение выделенных ресурсов.


## Задание 2. Обновить приложение

1. Создать deployment приложения с контейнерами nginx и multitool. Версию nginx взять 1.19. Количество реплик — 5.
2. Обновить версию nginx в приложении до версии 1.20, сократив время обновления до минимума. Приложение должно быть доступно.
3. Попытаться обновить nginx до версии 1.28, приложение должно оставаться доступным.
4. Откатиться после неудачного обновления.

## Решение

Создаем deployment.

```bash
kubectl create deployment nginx \
    --image=nginx:1.19 \
    --replicas=5 \
    --dry-run=client -o yaml > deployment.yaml
```

Добавляем второй контейнер (`multitool`) в манифест.

Фрагмент Deployment:

```yaml
containers:
- name: nginx
  image: nginx:1.19

- name: multitool
  image: wbitt/network-multitool
  env:
      - name: HTTP_PORT
      value: "8080"
```

Применяем:

```bash
kubectl apply -f deployment.yaml
```

Проверяем:

```bash
kubectl get deployment
kubectl get pods
```

## Обновление nginx до версии 1.20

Для минимального времени обновления изменяем стратегию:

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 0
    maxSurge: 1
```

Обновляем образ:

```bash
kubectl set image deployment/nginx nginx=nginx:1.20
```

Контролируем обновление:

```bash
kubectl rollout status deployment/nginx
```

Проверяем:

```bash
kubectl get pods
```

![](img/img_2.png)

---

## Попытка обновления до nginx:1.99

Запускаем обновление:

```bash
kubectl set image deployment/nginx nginx=nginx:1.99
```

Контролируем процесс:

```bash
kubectl rollout status deployment/nginx
```

Проверяем состояние:

```bash
kubectl rollout history deployment/nginx
```

Если обновление оказалось неуспешным:

```bash
kubectl get pods
```

Можно увидеть Pods в состоянии:

```
ImagePullBackOff
```

или

```
ErrImagePull
```

При этом приложение остается доступным, так как старые Pod продолжают работать.

![](img/img_3.png)

---

## Откат

Выполняем rollback:

```bash
kubectl rollout undo deployment/nginx
```

Проверяем:

```bash
kubectl rollout status deployment/nginx
```

История ревизий:

```bash
kubectl rollout history deployment/nginx
```

Проверяем образ:

```bash
kubectl describe deployment nginx
```

Получаем:

```
Image: nginx:1.28
```
